# 可重复性能分析与优化

目标不是“做一处看似更快的修改”，也不是单纯记录耗时，而是在保持语义和可维护性的前提下，用热点证据识别冗余，再通过可重复测量消除已证实的不必要工作。

## 1. 先确定边界

- 阅读项目 AGENTS.md、现有设计、测试和 profile 约定。
- 明确用户要分析、给建议还是实际实施；仅分析或方案讨论时，不修改生产代码。
- 固定工作负载、输入模型、规模、步长、编译配置、校验和及运行环境。
- 列出不得改变的语义：数值结果、采样时点、错误/取消行为、撤销/重做、持久化和历史结果。
- 不把不同负载、不同机器或不同构建方式的结果直接比较。

## 2. 建立基线

- 使用项目标准 Release 可执行文件直接测量，不在调试器中计时。
- 同时保存总耗时和归一化耗时，例如每步、每元素步、每次绑定。
- 输出应包含操作名、迭代数、总耗时、归一化耗时及防止结果被优化掉的 checksum。
- 使用项目现有 profile 入口；新增场景必须有明确输入、输出和运行命令，并随项目保存工具及结果。
- 即使本阶段没有优化任务，也必须审查热点分布、调用次数或分阶段测量，记录是否存在重复解析、分配、复制和不必要遍历；只有耗时表不算完成性能审查。
- 基线异常时先修复测量场景或说明环境，不在不稳定基线上宣称收益。

## 3. 用第二视角定位热点

按工具可用性选择采样 profiler、插桩 profiler 或分阶段计时。对 GCC/MinGW 可在独立构建目录使用 `-O3 -g -pg` 和链接 `-pg`，再以 gprof 读取结果；不要覆盖正常 Release 构建。

- 区分 self-time 与 inclusive time，不把 inclusive 子阶段相加。
- 区分生产耗时与插桩开销；插桩自身热点不能当成生产热点。
- 调用次数和路径可用于确认重复工作，但小函数采样归属可能有噪声。
- 热点既可能是计算，也可能是分配、引用计数、容器元数据复制、重复名称解析、重复校验或上下文建立。
- 不预设“加索引”“加缓存”“加同名特判”就是答案。

## 4. 找固定语义与重复工作

沿调用链问：

1. 哪些值在编译后、运行期间或整个文档中固定？
2. 哪些工作在每一步、每个元素或每个阶段重复推导？
3. 相同信息是否被多次规范化、查找或复制？
4. 是否存在坐标/布局/映射可以在计划阶段建立？
5. 是否存在同一输入被多个容器或平行模型重复表达？
6. 成功路径是否创建了只有错误路径才需要的对象？

优先考虑消除工作，而不是让重复工作稍微更快。

## 5. 审查优化方案的语义边界

修改前写出哪些处理被移除，以及为什么不会影响结果：

- 哪些信息在编译后固定，可以进入不可变执行计划？
- 哪些状态必须随每次运行、阶段或元素重新计算？
- 优化是否引入需要手工失效的跨编辑缓存？优先避免。
- 历史结果、数组值和外部输出是否保持原有内容与不可变性？
- 错误应继续在原阶段产生，还是确实允许提前？检查现有测试、诊断位置和失败前缀。

Qt/C++ 性能注意：

- QVector 写时复制通常避免立即深拷贝，但引用计数、元数据复制和分离仍有成本。
- 热路径中的 std::function 捕获过多可能超过实现的小对象存储并引入堆分配；测量后再调整捕获结构。

## 6. 先写方案，再分阶段实施

在 history 中建立带完整本地时间的计划，在设计文档中记录当前/目标不变量。每个阶段应有：

- 一个明确热点和一种结构性改动；
- 独立分支、测试保护和同场景 profile；
- 数值、边界、错误、取消、撤销/重做及持久化等适用回归；
- Release 后 Debug 全量测试；
- 自我审核后停止，等待用户审核。

不要在一个提交中混入多个无法归因的优化。未经当前授权，不自动提交、合并或推送。

## 7. 处理测量波动和回退

- 保留所有原始轮次，不删除不符合预期的结果。
- 若未修改场景也同步变慢，优先考虑系统负载、热降频或测量环境，不归因于当前代码。
- 需要时使用明确且一致的冷却间隔复测；报告测量条件和异常，不选择性平均。
- 若实现稳定回退，先分析新增间接调用、分配、复制和分支成本；必要时重做或撤回该方案，不把回退包装成优化。
- 不用单次最好结果代替可重复结论。

## 8. 记录完整过程与最终对比

主 profile 文档必须包含原始与优化后的总耗时、归一化耗时和变化比例，并链接详细报告。

合并完成后，按 AGENTS.md 使用 `git branch -d` 删除已合并且不再需要的本地分支；当前分支和仍含未合并依赖改动的分支不删除，远程分支不自动删除。删除本任务专用的临时构建、调试、profiler 和结果输出目录/文件，包括仓库外为本任务创建的目录；保留标准 Release/Debug 构建目录及正式 profile 记录。

history 计划不仅写方案，还应补充实际过程：

- 每阶段的实现、分支、提交和测试；
- 初始方案与新证据冲突时的设计修正；
- 异常轮次、冷却条件、性能回退及其处理；
- 最终两轮或稳定轮次对比和合并结果。

当前设计文档只保留最终有效约定，不用 history 代替当前设计，也不把过程细节堆回设计文档。

## 完成检查

- [ ] 基线、负载、校验和、工具和环境可重复。
- [ ] 热点有实际测量证据，未只凭直觉加索引/缓存。
- [ ] 优化前后的语义、固定信息和失败行为已审查。
- [ ] 每阶段独立实现、测试、profile 和审核。
- [ ] Release 后 Debug 全量通过；环境失败明确保留。
- [ ] 主 profile 有优化前后总耗时和归一化耗时。
- [ ] history 记录实际过程、异常和修正，不只是计划。
- [ ] 未越权提交、合并、推送或修改生产代码。

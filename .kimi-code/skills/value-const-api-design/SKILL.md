# 值语义与 const 接口设计

目标是在接口边界明确“可读取、可修改、可独立保存”的含义，避免通过非 const 引用或内部指针意外泄漏可变状态。

## 1. 先分类对象

- **纯值对象**：可以复制、比较和独立保存，例如设置、坐标、结果序列。
- **当前受控状态**：由 Document/Controller 等所有者通过命令修改，外部只读。
- **发布后的历史事实**：Run、ChangeRecord、编译计划等，发布后不可变。
- **唯一/多态对象**：AST、DocumentElement、QObject 等，可能不可复制，不能机械套用值返回。
- **构建期可变对象**：Builder 或局部 DTO 只在建立阶段可变，发布时冻结。

不要因为“当前代码会修改字段”就把历史对象归类为可变，也不要给所有纯值字段机械增加无收益封装。

## 2. 选择接口形式

按以下顺序判断：

1. 调用方需要独立保存结果且值复制成本合理：优先值返回。
2. 只在当前调用读取较大对象：使用 const 引用，明确所有者寿命。
3. 对象不可复制、多态或查询可能失败：可以使用 const 对象指针，但只在当前调用栈即时使用。
4. 对象必然存在且不可复制：引用比可空指针更准确。
5. 需要修改所有者状态：通过受控方法/命令，不暴露非 const 容器或内部字段。

对外接口尽量提供 const 方法和只读范围。私有可变查找、friend 执行边界和受控写接口不能变成绕过不变量的公共通道。

## 3. 值返回不等于必然昂贵

- Qt QVector/QString 等隐式共享容器通常只复制控制结构；调用方修改时才分离。
- ArrayValue 等嵌套值也要逐层考虑写时复制。
- std::vector、独特指针树和多态对象不享受上述规则。
- 返回值能消除内部节点寿命依赖，但不要为热点以外的接口引入无意义复杂包装。
- 如果性能存疑，使用 `measured-performance-optimization` 单独测量，不凭直觉选择指针。

## 4. 审核缺失与空结果语义

先检查调用方是否真的需要区分：

- 名称不存在；
- 对象存在但结果为空；
- 类型不符；
- 尚未计算或计算失败。

若不需要区分，直接返回空值/空容器即可，不机械增加 optional 或 found。若确有需求，可使用 `std::optional<T>`、显式 `bool &found` 或分离的存在性查询；选择能最清楚表达业务语义的形式。不要用多个隐式状态迫使调用方猜测。

## 5. 不可变发布与修改

- 构造或编译阶段完整校验，再一次性发布。
- 历史对象不得保留公开写通道；补充元数据时返回新对象，原对象不变。
- 值返回后，原所有者销毁不应使返回值失效。
- 修改返回值不能改写历史对象；容器的分离行为属于预期值语义。
- Document 修改后旧指针/引用是否失效必须明确，需要时重新按稳定 ID 查询。

## 6. 验证

按适用范围覆盖：

- 正常值、空值、缺失、类型不符和零样本；
- 返回值在原对象销毁后仍可使用；
- 修改返回值不影响原对象；
- 只读接口不能修改所有者状态；
- 历史对象的元数据、数值和名称保持；
- 撤销/重做、持久化及多 Run 对齐不回归。

## 完成检查

- [ ] 对象已按纯值、受控状态、历史事实或唯一对象分类。
- [ ] 接口形式与实际复制成本、修改语义一致。
- [ ] 没有用非 const 引用或内部指针绕过所有者。
- [ ] 缺失/空结果确有需求时才增加 optional/found。
- [ ] 新接口有正常、边界和独立性测试。
- [ ] 仅审查或讨论时未修改生产代码。
